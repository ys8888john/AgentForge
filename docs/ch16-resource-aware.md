# 第十六章：资源感知优化（Resource-Aware Optimization）

> 对应《Agentic Design Patterns》第十六章。实现文件：`agentd/src/resource/mod.rs`（策略层）+ `agentd/src/patterns/resource_aware.rs`（模式层）。

---

## 1. 这一章解决什么问题

前面的模式都在追求"把事做好"，本章追求的是"**值不值这个价**"。

> 资源感知优化使 Agent 能够动态监控和管理计算、时间和财务资源。
> 这与规划不同——规划关注**动作序列的安排**，本章关注**在预算内如何分配资源**。

典型的两难：所有请求都上"最重的一套"（开思考 + 长生成），简单问题也在烧几千 token；
反过来一刀切地省，复杂问题就答崩。本章要的是**按复杂度动态分配预算**。

### 与相邻章节的区别

| 章节 | 关心什么 | 失败时怎么做 |
|------|---------|-------------|
| Ch2 路由 | 按**任务类型**分发到不同提示词（同一模型） | — |
| Ch6 规划 | **动作序列**（先做什么后做什么） | — |
| Ch12 异常恢复 | **能不能成功**（出错后重试同一套配置） | 重试同一动作 |
| **Ch16 资源感知** | **值不值这个价**（主动按复杂度分配预算） | **退到更省的策略** |

## 2. 本机现实：没有第二个模型，资源杠杆在哪？

书里的例子是 Gemini Flash ↔ Gemini Pro 两个真实模型做切换。
本机只装了 `qwen3:8b`，没有第二个模型可供切换。

但**资源杠杆不只有"换模型"这一条**，对 qwen3 而言更重要的是：

| 杠杆 | 影响 |
|------|------|
| `think`（思考开关） | **最大杠杆**：一开就是数千 token。本项目历史上正是它把内存吃到 21GB |
| `num_predict`（生成上限） | 直接决定生成量与最坏耗时 |
| 提示策略 | 给轻量档一个"请详尽分析"的提示，等于逼它超支 |
| `model`（模型） | **预留接口**：填了本地没有的模型会失败并触发降级 |

因此实现为「**档位（Tier）× 策略**」：
每个档位 = 一组资源参数。将来若装了小模型，只需在 `tier_policy` 里填 `model`，
模式代码一行都不用改。

### 档位表

| 档位 | 思考 | 生成上限 | 首响超时 | 提示策略 |
|------|------|---------|---------|---------|
| **轻量 Light** | 关 | 512 | 30s | "直接、简洁地回答，不要展开背景" |
| **标准 Standard** | 关 | 1536 | 60s | "条理清晰，分点说明，不必过度展开" |
| **深度 Deep** | 开 | 4096 | 120s | "充分分析，逐步推理，比较方案并说明取舍" |

复杂度映射：`simple → light`、`medium → standard`、`complex → deep`。

## 3. 执行流程

```text
① classify  用极省的一次调用判定复杂度（simple / medium / complex）
             └ 分类器失败 / 输出无法解析 → 启发式兜底
② plan      复杂度 → 档位，套用总预算约束（token_budget）
③ execute   按档位参数执行（思考开关 / 生成上限 / 提示策略）
             └ 失败 → 沿档位链降级（deep → standard → light）重试
④ fallback  三档全败 → 默认模型 + 关思考 的最终兜底
⑤ report    报账（耗时 / 输出量 / 预算使用率 / 是否降级）
```

### ① 分级本身也必须便宜

分级用的参数：关思考 + `num_predict: 32` + 首响超时 20s。
否则"为了省资源而先烧一笔"就本末倒置了。

分级失败**不算错误**——Ollama 不可用或输出无法解析时回落到
`heuristic_complexity()`（按输入长度、问句数量、关键词信号粗判）。
复杂度分级只是优化手段，不该成为单点故障。

### ② 预算约束

`token_budget` 是请求级总预算，所有档位的生成上限都不会超过它。
实测：同一道"详细描写春天"的题，预算 200 相比无预算，
耗时从 36.2s 降到 3.7s（**快约 10 倍**）。

### ③ 降级链

```
Deep --失败--> Standard --失败--> Light --失败--> 最终兜底
```

降级时会 yield 一条 `degrade` 事件说明原因，
并**清空上一档的半截输出**重新生成（否则会拼接出半截答案）。

## 4. 本章挖出的两个真实 Bug（重要）

### Bug 1：`num_predict` 一直没生效

Ollama 的生成参数必须放在 `options` 对象里，**放顶层会被静默忽略**——
不报错、不警告，就是不起作用。

实测同一 prompt + `num_predict: 20`：

| 写法 | 输出 |
|------|------|
| 顶层 `"num_predict": 20` | 626 字符（**没生效**） |
| `"options": {"num_predict": 20}` | 28 字符（正确截断） |

修复前本项目一直用的顶层写法，意味着 `llm.rs` 注释里那条
"num_predict 作为兜底上限防止生成失控"**从未真正生效过**。
是 Ch16 做预算约束时才发现（预算 200 却输出了 3414 字符）。

**副作用**：修复后所有模式的超长生成会被真正截断在 4096 token
（此前该上限形同虚设）。这是修复，符合原注释意图，但行为确实变了。

### Bug 2：思考会吃光预算，导致"只想不答"

qwen3 的思考与正文**共用** `num_predict` 配额，且思考**优先**占用。

实测同一道题、预算 200 + 深度档（开思考）：

```
思考 528 字符，正文 0 字符   ← 预算全花在想上了，一个字都没答出来
```

对照无预算（4096）时：思考 1259 字符 + 正文 1660 字符。

**修复**：预算低于 `MIN_BUDGET_FOR_THINKING`（1024）时强制关闭思考。
宁可答得浅，也不能答不出来。修复后同样条件：

```
思考 0 字符，正文 494 字符，耗时 3.7s   ← 正常作答
```

plan 事件会显式说明"思考关闭（预算不足，已自动关闭）"，
避免与用户在 `tier_policy` 里显式配置的 `think: false` 混淆
（用户显式指定的优先，不被自动干预）。

## 5. 事件契约

新增一个事件：

```rust
AgentEvent::Resource { phase: String, text: String }
```

SSE 编码：`event: resource` + `data: <phase>:<text>`

| phase | 含义 | text 示例 |
|-------|------|----------|
| `classify` | 复杂度判定结果 | `简单（模型判定）` / `中等（启发式兜底）` / `复杂（手动指定档位）` |
| `plan` | 选中的档位与预算 | `深度档｜思考开启｜生成上限 4096` |
| `degrade` | 降级到更省的档位 | `深度档 调用失败，降级至 标准档｜原因：…404 not found` |
| `usage` | 最终消耗统计 | `耗时 4.5s｜输出 331 字符｜预算使用率约 83%（上限 200 token）｜LLM 调用 2 次` |

其余复用 `Thought`（仅深度档有）、`Token`、`Done`。

### 前端注意：degrade 时必须重置 token 累加器

降级意味着上一档输出作废、要重新生成。若前端不重置 `tokenAcc`，
新输出会**追加**到旧输出后面，变成"半截答案 + 新答案"。
`page.tsx` 中已处理：收到 `phase === "degrade"` 时清空累加器。

## 6. 实测数据

同一系统、不同复杂度问题的资源消耗：

| 输入 | 分级 | 档位 | 耗时 | 输出 | 预算使用率 |
|------|------|------|------|------|-----------|
| 中国的首都是哪里？ | simple | 轻量（关思考/512） | **0.2s** | 3 字符 | ~0% |
| 列举三个提高团队效率的方法 | medium | 标准（关思考/1536） | 2.4s | 220 字符 | ~7% |
| 对比端侧小模型与云端大模型的取舍 | complex | 深度（开思考/4096） | 40.0s | 4072 字符 | ~50% |

**简单问题 0.2 秒解决，复杂问题才花 40 秒深度思考** —— 这就是本章的价值。

预算对比（同一道复杂题）：

| 预算 | 输出 | 耗时 |
|------|------|------|
| 无限制（4096） | 4072 字符 | 36.2s |
| 200 | 331 字符 | 4.5s |

降级验证（深度档配一个不存在的模型）：

```
plan:    深度档｜思考开启｜生成上限 4096
degrade: 深度档 调用失败，降级至 标准档｜原因：Ollama 返回错误 404 Not Found: model 'no-such-model:999b' not found
usage:   耗时 22.9s｜输出 2179 字符｜LLM 调用 3 次｜已降级
```

## 7. 已知限制 / 后续可做

1. **没有真正的多模型**。本地只有 `qwen3:8b`，`tier_policy.*.model` 字段已预留，
   装了第二个模型即可启用（建议 pull 一个 1.5B 级小模型做 light 档）。
2. **预算用字符数近似 token**。本地 Ollama 不回传精确 token 计数，
   故 `budget_usage_pct()` 按 `CHARS_PER_TOKEN = 2.0` 粗算并标注"约"。
   注意：早期版本直接拿字符数除以 token 预算，算出过 142%、854% 这种荒谬值（已修）。
3. **分级结果无交叉校验**。目前 LLM 判定优先、启发式仅作兜底。
   可考虑：LLM 说"简单"但输入超长时，以启发式为准。
4. **无历史学习**。书里提到用「批评 Agent」评估回答质量、
   反馈给路由器以改进分级。可结合 Ch9 学习适应做"哪类问题该给多少预算"的长期优化。
5. **无并发预算**。多个会话同时跑时，预算是单请求维度，没有全局配额/限流。

## 8. 与其他章节的关系

- **可包裹 Ch12 异常恢复**：两者互补，Ch16 管"花多少"，Ch12 管"失败了怎么办"。
- **可与 Ch15 A2A 结合**：A2A 的 `AgentCard.model` 已支持每 Agent 独立模型，
  加上本章的档位策略，可实现"按子任务复杂度给不同 Agent 分配不同预算"。
- **与 Ch9 学习适应的接口**：把历次 `usage` 存进偏好画像，
  即可实现书里说的"学习型资源分配策略"。
